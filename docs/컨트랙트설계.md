# 7단계 컨트랙트 설계 — FairReview 최소판

파일: `contracts/contracts/FairReview.sol`
먼저 **Remix VM**(브라우저 안 가상 블록체인, 무료)에서 직접 눌러 보고, 그다음 **Hardhat** 프로젝트로 옮긴다.
Sepolia 배포 · Hardhat 테스트 · 화면 연결은 8단계, AI 오라클 서명 검사는 10단계.

## 1. 누가 무엇을 하나

| 역할 | 지갑 | 할 수 있는 일 |
|---|---|---|
| 관리자 | 배포한 사람 (`admin`) | 가게 등록 `registerStore` · 비상 중지 `pause` / `unpause` |
| 사장님 | 등록된 가게의 `owner` | 자기 가게 결제 기록 `recordPayment` → 손님에게 1% 포인트 |
| 손님 | 결제 기록의 `customer` | 그 결제로 리뷰 한 번 `submitReview` → 별점과 상관없이 10포인트 |

포인트(`points`)에는 **보내기 함수가 없다** → 사고팔 수 없고, 리뷰를 포인트로 사는 것도 막힌다.

## 2. 리뷰 관문 (submitReview 순서)

| # | 검사 | 걸리면 |
|---|---|---|
| ① | 결제 기록이 있는가 | `PaymentNotFound` |
| ② | 그 결제의 손님 본인인가 | `NotPaymentCustomer` |
| ③ | 이 결제로 이미 쓰지 않았나 | `AlreadyReviewed` |
| ④ | 결제 후 30일 이내인가 | `ReviewExpired` |
| ⑤ | 별점 1~5, 내용 1~900바이트 | `InvalidRating` · `EmptyContent` · `ContentTooLong` |

결제 기록 때: 손님 주소 0 금지(`ZeroAddress`), 금액 1~1천만(`InvalidAmount`), 사장님 본인 결제 금지(`SelfPayment`).

## 3. Remix 에서 해 볼 시나리오 (Remix VM 계정 4개)

| 순서 | 계정 | 함수 | 넣을 값 | 결과 |
|---|---|---|---|---|
| 1 | 계정1 (관리자) | Deploy | — | 배포 |
| 2 | 계정1 | `registerStore` | 계정2 주소, `온정 김치찌개` | `storeCount` = 1 |
| 3 | 계정3 | `recordPayment` | `1`, 계정3 주소, `9000` | ❌ `NotStoreOwner` (사장님이 아님) |
| 4 | 계정2 (사장님) | `recordPayment` | `1`, 계정3 주소, `9000` | `points(계정3)` = 90 |
| 5 | 계정4 | `submitReview` | `1`, `5`, `맛있어요` | ❌ `NotPaymentCustomer` (결제 안 한 사람) |
| 6 | 계정3 (손님) | `submitReview` | `1`, `5`, `김치찌개 9천원, 국물이 진했어요` | `points(계정3)` = 100 |
| 7 | 계정3 | `submitReview` | 같은 값 한 번 더 | ❌ `AlreadyReviewed` |
| 8 | 계정2 | `recordPayment` | `1`, 계정2 주소, `9000` | ❌ `SelfPayment` |

관찰 과제 (7주차): 주황 버튼과 파란 버튼은 왜 색이 다른가? 아무 주소로 `points` 를 조회하면 왜 0 인가?

## 4. 취약 → 안전 비교 (일부러 틀려 보기)

`submitReview` 의 두 줄을 `//` 로 막고 다시 배포해서 3번 시나리오를 반복한다.

```solidity
// if (p.reviewed) revert AlreadyReviewed(paymentId);   // ③
...
// p.reviewed = true;
```

→ 같은 결제로 리뷰를 몇 번이고 쓸 수 있고, 쓸 때마다 10포인트씩 늘어난다 (영수증 한 장으로 리뷰 도배).
두 줄을 되살리면 두 번째부터 `AlreadyReviewed` 로 막힌다.
**이 결과(포인트 숫자 · 오류)를 캡처**해서 무엇이 달라졌는지 직접 적는다.
