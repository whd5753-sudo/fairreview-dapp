# 10단계 AI 오라클 설계 — AI 판정을 컨트랙트가 믿게 만들기

## 1. 왜 필요한가 (9단계 보안 점검 T1)

8단계까지 AI 판정은 **화면에만** 있었다. Remix · Etherscan 에서 `submitReview` 를 직접 부르면 광고 · 과장 리뷰도 그대로 기록된다.
블록체인은 AI 를 돌릴 수 없으므로, **체인 밖 오라클 서버**가 AI 판정 점수에 서명하고 **컨트랙트는 그 서명만 확인**한다.

```
[손님 화면] ─ 리뷰 ─▶ [AI 오라클 서버]  4단계 엔진으로 점수 계산 → 오라클 개인키로 서명
     ▲                       │ { score, signature }
     └───────────────────────┘
[손님 화면] ─ submitReview(결제, 별점, 내용, 점수, 서명) + MetaMask 서명 ─▶ [FairReview 컨트랙트]
                                     ⑥ 서명한 사람 == oracle 인가?  ⑦ 점수 < 700 인가?
                                     → 400 미만 게시(+10P) / 400~699 보류(관리자 검토)
```

## 2. 서명하는 내용

`keccak256(abi.encode(태그, 체인 id, 컨트랙트 주소, 결제 번호, 리뷰 쓰는 사람, 별점, keccak256(내용), 점수))`
→ EIP-191 (`\x19Ethereum Signed Message:\n32` + 해시) 로 서명. 컨트랙트: `verdictDigest` + OpenZeppelin `MessageHashUtils` · `ECDSA.tryRecover`.
오라클 쪽: `oracle/sign.mjs` (Hardhat 테스트도 이 파일로 서명 → 두 쪽 형식이 다르면 테스트가 실패).

| 들어가는 값 | 막는 공격 |
|---|---|
| 태그 `FairReview.AIVerdict.v1` | 오라클 키로 한 다른 서명을 리뷰 서명으로 쓰기 |
| 체인 id · 컨트랙트 주소 | 다른 체인 · 다른(옛) 컨트랙트에서 받은 서명 재사용 (테스트 F5) |
| 결제 번호 · 리뷰 쓰는 사람 | 남의 서명 · 다른 결제의 서명 가져다 쓰기 (F5) |
| 별점 · 내용 해시 · 점수 | 좋은 점수를 받은 뒤 내용 · 별점 · 점수 바꾸기 (F4) |
| (결제당 한 번 `reviewed`) | 같은 서명으로 두 번 제출 (C4) |

## 3. 컨트랙트 변경 (`contracts/contracts/FairReview.sol`)

| 변경 | 이유 |
|---|---|
| `constructor(address oracle_)`, `oracle` · `admin` 을 `immutable` | 오라클 주소를 배포 때 고정. `admin` immutable 은 9단계 Slither 제안 |
| `submitReview(…, uint16 score, bytes signature)` + 관문 ⑥ `InvalidOracleSignature` · ⑦ `SuspectedFakeReview` · `InvalidScore` | AI 판정 우회 차단 |
| `reviewStatus` (없음 · 게시 · 보류 · 거절), 이벤트 `ReviewHeld` | 400~699 는 바로 게시하지 않고 보류 |
| `resolveHeld(결제, 승인?)` — `onlyAdmin` | 보류 리뷰를 사람이 검토. 사장님은 이해관계가 있어 검토 권한 없음. 승인 때 +10P |
| `ReviewSubmitted` 에 `aiScore` 추가 | 화면 · 탐색기에서 점수를 볼 수 있게 |
| OpenZeppelin Contracts 5.6.1, `evmVersion` cancun | 검증된 서명 라이브러리 (서명 가변성 · 잘못된 v 값 처리) |

## 4. 오라클 서버 (`oracle/`)

| 파일 | 하는 일 |
|---|---|
| `keygen.mjs` | 오라클 전용 테스트 지갑 생성 → `oracle/.env` (이미 있으면 덮어쓰지 않음, 개인키는 화면에 안 나옴) |
| `server.mjs` | `POST /sign` → 4단계 엔진으로 판정 → 서명. `GET /health`. 127.0.0.1 에서만 열림, CORS 는 `localhost:5173` · `whd5753-sudo.github.io` 만, 요청 4KB 제한, 체인은 Sepolia · 로컬만 |
| `judge.mjs` | 입력 검사(결제 번호 · 주소 · 별점 · 900바이트) → `analyzeText` · `decide` → 서명 |
| `sign.mjs` | 서명 형식 (컨트랙트와 같음) |
| `oracle.test.mjs` | O1~O4: 서명 복구 · 기대값 표 점수 · 한 글자 위조 · 잘못된 입력 |

- 개인키는 `oracle/.env` 에만. `.gitignore` 의 `.env` 로 커밋 안 됨, `.claude/settings.json` 이 Claude 의 읽기를 막음, CI 가 `.env` 커밋 여부 검사.
- 오라클 지갑은 **서명만** 한다 → ETH 가 필요 없다. MetaMask 지갑과 따로다.
- 오라클은 "이 결제가 이 손님 것인가"는 확인하지 않는다 → 컨트랙트 관문 ①~④가 확인.

## 6. Sepolia 가스 — 로컬보다 훨씬 비싸다 (8단계 실제 기록)

| 작업 | 로컬 Hardhat | Sepolia 실제 |
|---|---|---|
| 배포 (v1) | 약 89만 | **1,105만** (코드 6,949바이트 — Remix 가 최적화 없이 컴파일) |
| registerStore | 약 9.5만 | 25.6만~35.4만 |
| recordPayment | 약 16.3만 | 68.6만 |
| submitReview | 약 4.4만 | 5.6만 |

Sepolia 는 새 저장 · 코드 저장 비용이 로컬 Hardhat(옛 규칙)보다 훨씬 크다 (배포 코드 1바이트당 약 1,590 가스).
**v2 를 배포할 때는 Remix 에서 최적화(Optimization 200)를 꼭 켠다** — 최적화 끄면 코드가 커져서 거래 한 건의 가스 한도(약 1,677만)에 가까워질 수 있다.
예상: 최적화 v2 약 5,742바이트 → 배포 약 950만~1,000만 가스 ≈ 0.015 SepoliaETH (1.5 gwei 기준).

## 7. 배포 순서 (사람)

1. `oracle` 폴더: `npm install` → `npm test` → `npm run keygen` → 출력된 **오라클 주소** 메모
2. Remix: `FairReview.sol` 붙여 넣기 → Compiler 0.8.24 · **Advanced → Optimization 켜기(200)** · EVM 기본값 → Compile (OpenZeppelin 은 Remix 가 자동으로 받음)
3. Environment = Browser Extension → Sepolia Testnet - MetaMask, Account 1 → Deploy 칸 `oracle_` 에 오라클 주소 → Deploy → 컨펌
4. 새 컨트랙트 주소 → `oracle/.env` 의 `ORACLE_CONTRACT=` 에 적기 (사람이 직접. Claude 는 .env 를 못 읽고 못 쓴다)
5. Account 1 로 `registerStore` (가게 1~3, 사장님 Account 2) → Account 2 로 `recordPayment` 2건 (게시용 · 보류 시험용)
6. 컨트랙트 주소를 Claude 에게 → 화면(10단계-3) 연결

## 8. 한계

- 오라클 서버가 사용자 PC 에서만 돈다 (켜져 있을 때만 리뷰 제출 가능). 실서비스라면 클라우드 서버 + 키 관리 서비스(KMS)
- 오라클 키가 유출되면 아무 점수나 서명할 수 있다 → 컨트랙트에 오라클 교체 함수가 없으므로 재배포. (실서비스라면 오라클 교체 · 여러 오라클 서명)
- AI 엔진 자체의 한계(4단계: "갓김치" 오탐 등)는 그대로 — 오라클은 판정을 **위조 못 하게** 할 뿐, 판정을 **정확하게** 만들지는 않는다
